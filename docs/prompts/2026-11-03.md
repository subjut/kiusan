# Prompt log

Verbatim log of the prompts given to the agent in this repository, grouped
per session day. The prompts are the project's steering history: they
survive agent-session compaction and can be handed to a fresh agent
verbatim.

Conventions:

- Prompts are quoted exactly as given, typos and all.
- A short note follows each prompt: what it produced or decided.
- Entries marked *(wording lost)* belonged to a compacted conversation
  whose summary preserved only the substance.
- Transcript markers like "function call failed" in Zed's thread history
  are failed agent tool calls (e.g. truncated write batches), not user
  prompts, and are not logged here.
- Entries are appended automatically with every prompt — verbatim plus
  a one-line outcome note, written before the session summary (rule in
  `AGENTS.md` → Conventions).

## 2026-11-03 — date/time localization

1. "Read AGENTS.md. How is date an time localization handled in this project. Specifically, on the 1-1-form, are they hard coded or are they displayed with the localization settings of the user's browser? How about on the poll answer page meet.html?"
   → Answered (no code change): the form's native date/time inputs
     render in the user's browser locale, while the `dater.js` calendar
     (month/weekday names, month title), chips and slot preview use
     hardcoded English + ISO `YYYY-MM-DD[THH:MM]` strings; the timezone
     `<select>` shows IANA names with the browser zone prefilled.
     `meet.html` is fully server-rendered in Go (`meetingHandler` in
     `main.go`) with English `time.Format` layouts in the poll's
     timezone — the viewer's locale plays no role there.
2. "The date and time should be displayed in the local browser localization on all pages. But there should be a dropdown on the form and poll answer pages, to change the default (maybe save it in an unpersonalized cookie)?
Write me an implementation proposal. Ask questions, if you are uncertaint about anything. Don't implement anything yet, but write the prompt log."

     poll's `timeZone` (viewer's own zone never used). Four clarifying

     the dropdown carries a curated ~15-locale list plus the browser's
     own language auto-added.

5. "Read AGENTS.md. It's time for localization. Date and time localization was added in the last commit. Now, the app should become multilingual.
There is a language drop down in the header. That should be prefilled with the browser locale settings. But the user may override it by selecting a different language, that gets stored in a cookie (already implemented) and changes the language of the interface. What is the best way to implement the multilanguage feature? Ask questions you are unsure about anything. Give me a proposal, potentially with options. Don't implement anything yet."
   → Wrote the multilingual-UI proposal (no code change): recommended
     server-side i18n (new `i18n/` package with embedded JSON catalogs,
     cookie → `Accept-Language` → en resolution, `{{t "key"}}` in the
     templates, server-rendered language dropdown with reload on change,
     an inline JSON blob for the `dater.js`/`poll.js` widget strings) over
     a client-side JS dictionary (no-JS stays English, two sources of
     truth); ~50 UI strings inventoried across the 3 templates + 2 JS
     files; asked the user to choose the architecture and which languages
     to ship first. Follow-up (user picked A, asked about the Fiber v3
     contrib i18n package and about preserving half-filled forms across a
     language-switch reload): all decisions settled, plan finalized (no
     code change) — **A″**: `gofiber/contrib/v3/i18n` (go-i18n v2, YAML
     catalogs in `localize/` via `EmbedLoader`, `LangHandler` hook:
     `kiusan-locale` cookie → `Accept-Language` → en); templates render
     through a `t` func + `data-i18n` markers, `lang`/title localized;
     language switch does **not** reload — a `GET /i18n/:lang` endpoint
     serves the dict live from the in-memory bundle (English fallback)
     and a generic client swapper (text/placeholder/title/aria-label
     nodes + `lang`/title + widget re-render; fetch failure → reload)
     preserves half-filled forms; initial `window.I18N` dict is
     server-inlined so widgets (dater/poll strings) translate from page
     load with zero per-page network. Maintenance contract: updating a
     translation = edit one YAML file + restart. First languages:
     **en + de only** (dropdown lists shipped languages + browser
     default; a later language = one YAML file + tag in
     AcceptLanguages); the single locale setting also drives the
     date-value locale (Intl).
