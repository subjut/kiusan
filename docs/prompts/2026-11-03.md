# Prompt log

Verbatim log of the prompts given to the agent in this repository, grouped
per session day. The prompts are the project's steering history: they
survive agent-session compaction and can be handed to a fresh agent
verbatim.

Conventions:

- Prompts are quoted exactly as given, typos and all.
- A short note follows each prompt: what it produced or decided.
- Entries marked *(wording lost)* belonged to a compacted conversation
  whose summary preserved only the substance.
- Transcript markers like "function call failed" in Zed's thread history
  are failed agent tool calls (e.g. truncated write batches), not user
  prompts, and are not logged here.
- Entries are appended automatically with every prompt — verbatim plus
  a one-line outcome note, written before the session summary (rule in
  `AGENTS.md` → Conventions).

## 2026-11-03 — date/time localization

1. "Read AGENTS.md. How is date an time localization handled in this project. Specifically, on the 1-1-form, are they hard coded or are they displayed with the localization settings of the user's browser? How about on the poll answer page meet.html?"
   → Answered (no code change): the form's native date/time inputs
     render in the user's browser locale, while the `dater.js` calendar
     (month/weekday names, month title), chips and slot preview use
     hardcoded English + ISO `YYYY-MM-DD[THH:MM]` strings; the timezone
     `<select>` shows IANA names with the browser zone prefilled.
     `meet.html` is fully server-rendered in Go (`meetingHandler` in
     `main.go`) with English `time.Format` layouts in the poll's
     timezone — the viewer's locale plays no role there.
2. "The date and time should be displayed in the local browser localization on all pages. But there should be a dropdown on the form and poll answer pages, to change the default (maybe save it in an unpersonalized cookie)?
Write me an implementation proposal. Ask questions, if you are uncertaint about anything. Don't implement anything yet, but write the prompt log."
   → Wrote the implementation proposal (no code change): client-side
     `Intl.DateTimeFormat` formatting in a new `static/js/locale.js` +
     `static/partials/locale-select.html` dropdown, included on the
     1-1 form and `meet.html` only; the server keeps the structural
     layout and today's English labels as no-JS fallback, adding
     `data-tz`/`data-slot`/`data-lines` attributes; locale resolution
     cookie (`kiusan-locale`, non-personalized, JS-only, 1-year Lax)
     first, then `navigator.language`; all values formatted with the
     poll's `timeZone` (viewer's own zone never used). Four clarifying
     questions all answered per the recommendations: date/time values
     only (UI text stays English), calendar week-start follows the
     locale best-effort (Sunday fallback), poll meta line gains a
     client-side UTC offset (e.g. "Europe Berlin (UTC+01:00)"), and
     the dropdown carries a curated ~15-locale list plus the browser's
     own language auto-added.
3. "Go ahead and implement."
   → Implemented the locale-aware date display (the proposal from entry 3):
     new `static/js/locale.js` + `static/partials/locale-select.html`
     (Display dropdown: curated ~15 locales + browser language
     auto-inserted; unpersonalized `kiusan-locale` cookie, JS-only,
     1-year Lax; locale = cookie → navigator.language); `meet.html` now
     carries `data-tz` on the container, `data-slot`/`data-lines` on the
     header cells, `data-slot` on the time sub-row, and `f-date` spans
     for the expiry dates, with `tz-name` gaining a client-computed UTC
     offset; `main.go` passes the raw IANA zone + expiry instant while
     keeping the English labels as the no-JS fallback; `dater.js` renders
     its calendar/chip/preview labels through `Intl` (locale week-start
     best-effort, Sunday fallback) and re-renders on locale change;
     `smoke_test.go` pins the new data-attribute contract (incl. the UTC
     instants), `poll_test.go` updated for the new meta/ended markup;
     `go build`, `go vet`, `go test -race ./...` all pass; the JS passes
     `node --check`. `AGENTS.md` gains the "Locale display"
     gotcha; `.gocache/` (project-local GOCACHE) gitignored. Note for
     future sessions: terminal now runs in WSL (go1.26.0 linux/amd64)

4. "Move the localization dropdown into the header. Change the names in the localization dropdown to simple names, e.g. English, Deutsch, Italiano, etc.
Since the date and time selection interfaces are provided by the browser, the selected localization in the dropdown does not have an effect on these. Is it possible to supply a localization parameter to the date and time selectors? Or is there another way to also display the selectors in the selected localization? Give me options before implementing this."
   → Moved the locale dropdown into the global site header (now on every
     page): `partials/header.html` includes `partials/locale-select.html`
     + `<script src="/locale.js">`; removed from 1-1-form.html and
     meet.html. `header .container` is now flex (wordmark left, dropdown
     right); `#locale` gets its own compact sizing. Dropdown options show
     native language names (English, Deutsch, Italiano, …) via a
     `LOCALE_NAMES` map while the value stays the BCP-47 tag; the
     "Browser default (…)" label uses the native name too. `locale.js`'
     initial `reformat()` now waits for `DOMContentLoaded` since the
     script parses before the page body. `smoke_test.go`: asserts
     `id="locale"` on `/` and slices the timezone `<select>` to its own
     `</select>` (the header select now precedes it). Build/vet/test
     pass, node --check clean. For the native pickers: confirmed there is
     no standard parameter to force `<input type=date|time>` into a locale
     (they follow the browser/OS); presented three options — accept it /
     locale-formatted value echo next to the native inputs / fully custom
     JS date+time pickers — and asked the user to choose before
     implementing.
