# Prompt log

Each user prompt, verbatim, numbered sequentially within the day, followed by a
one-line note of what it produced or decided.

1. "Read AGENTS.md. When the answer table gets really big, the user always has to scroll up to see the header with the dates/voting options. What would be the best way to keep the header of the answer table in view, when the user scolls down? Make me an inplementation proposal, ask questions and give me options to decide on, and give me the final options on how to proceed."

   proposed two approaches (bounded scroll box with pinned `thead` vs. a JS
   cloned sticky header); the user chose the bounded box, pinning all of the
   meeting's header rows (year/date/time), without pinning the form row to the
   bottom. Implemented: `.table-scroll` became the table's bounded vertical
   scroller (`max-height` + `overflow: auto`), the `thead` pins via `position:
   sticky` per row (tops from row heights measured in `page.js` as `--th-2`/
   `--th-3`, activated by the `table-sticky` class, re-measured on resize and
   on `Locale.onChange`), and `.answers-table` switched to
   `border-collapse: separate` for Chrome's sticky-border bug (visually a
   no-op — cells draw only right + bottom borders). Verified: go
   build/vet/test, node --check, jstest 40/40 (new sticky-activation test),
   server on test.db serving the 100×100 table 200; AGENTS.md updated (Layout,
   jstest bullet, new Sticky table header gotcha).

2. "The language dropdown selector has "Browser default" as an option. This is not idea. It should reflect the actually detected and/or selected language. Give me the best options on how to implement that and provide choices for edge cases or anything that is unclear."

   Proposed Option A (drop the "Browser default" row; the selected option is
   always the effective language, server-resolved + client-corrected) and
   Option B (keep one browser-following row labeled with the detected
   language); the user declined the question and proposed a hybrid of their
   own (next entry).

3. "I have another option: drop the "Browser default" from the UI entirely, like option A, but don't set a language cookie, unless the user explicitly selects another language. Also, when a user switches back to the browser default language, delete the cookie again. This follows the principle, to store a little data as possible, while still offering full functionality. Would that proposal work? Are there drawbacks? Ask me option for edge cases or unclear things."

   Hybrid adopted: the row disappears; the selected option is the effective
   language (server-rendered cookie → Accept-Language → English, client-synced
   on load); a cookie pin is written only when the pick deviates from the
   server-rendered implicit language (a `data-implicit` attribute on the
   select, per user decision — raw navigator matching stays out of JS) and
   deleting it happens when the user switches back to it; a browser language
   with no shipped catalog stays implicit in the English fallback (no cookie,
   per user decision). Implemented: the `value=""` row is gone, the select
   carries `data-implicit` (i18n.go's new `implicitLang`: Accept-Language →
   shipped → English), `renderPage` marks the resolved language selected
   (`localeChosen` deleted), `locale.js` re-syncs the selection on load and
   pins/un-pins the `kiusan-locale` cookie against `data-implicit` (the
   `""`-fetch special case is gone); `nav.browserDefault` dropped from both
   catalogs. Verified: go build/vet/test (new dropdown selected-state +
   data-implicit assertions in i18n_test.go), node --check, jstest 41/41
   (new effective-language-sync + pin/un-pin tests, the browser-default test
   rewritten); AGENTS.md updated (both Commands test bullets, the render.go /
   i18n.go / locale.js layout entries, the Locale display + Interface
   localization gotchas).
