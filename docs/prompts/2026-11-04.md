# Prompt log

Verbatim log of the prompts given to the agent in this repository, grouped
per session day. The prompts are the project's steering history: they
survive agent-session compaction and can be handed to a fresh agent
verbatim.

Conventions:

- Prompts are quoted exactly as given, typos and all.
- A short note follows each prompt: what it produced or decided.
- Entries marked *(wording lost)* belonged to a compacted conversation
  whose summary preserved only the substance.
- Transcript markers like "function call failed" in Zed's thread history
  are failed agent tool calls (e.g. truncated write batches), not user
  prompts, and are not logged here.
- Entries are appended automatically with every prompt — verbatim plus
  a one-line outcome note, written before the session summary (rule in
  `AGENTS.md` → Conventions).

## 2026-11-04 — poll lifecycle (close / re-open / delete)

1. "Read AGENTS.md.
On the meeting admin page, add a button \"Close poll\". It should close the poll, so that nobody can respond any more, but the public and admin links should still be accessible and display the answer table. Additionally, on the admin page, if a poll is closed, add a button \"Re-open poll\", so that new answers can be added or existing answers can be edited/deleted.
And lastly, on the admin page, add a button \"Delete poll\". When clicked, it shows a big warning, that all data pertaining to that poll will be deleted. If the user confirms, all data belonging to that poll should be purged from the database, including all answers, cookie identity data, etc. There should also be a new 404 error page for when a user goes to a link of a deleted poll. That error message should be different from other 404 errors."
   → Implemented the admin poll lifecycle: `Meeting.Closed` column
     (additive-only AutoMigrate, carried in the CAS `Update`); new
     capability routes `POST /meet/+/close|reopen|delete` (admin key
     only, no CSRF) — close blocks answering (410 on all three answer
     endpoints, no new identity cookie) while both links keep showing
     the answers table as a static matrix; re-open restores
     answering/editing/deleting; delete purges the row (answers +
     stored identities) and expires the requesting browser's identity
     cookie, redirecting to `/`. Admin page gains "Close poll" /
     "Re-open poll" (state-dependent) and a "Delete poll" button that
     opens a big inline `role=alert` warning (JS-gated two-step
     confirm). The answers table was extracted to
     `static/partials/answers-table.html` (shared by the live form and
     the closed poll's read-only matrix; row icons render only while
     the poll is open). A deleted link (`GET /meet/+` and
     `GET /1-1-form/edit/+`) now renders the new
     `static/meet-gone.html` with a 404 status and its own message
     (`meetingGone`); unknown paths keep the plain-text 404. i18n: new
     en+de keys (`meet.closePoll/reopenPoll/deletePoll/deleteWarn/
     deleteConfirm/closedPre/closedPost`, `pagetitle.meetGone`,
     `meet.goneTitle/goneText/goneHome`). CSS: amber `.closed` notice,
     `.btn-danger`, `.delete-warning`; poll.js wires the two-step
     warning. Tests: the `runPollSuite` walkthrough gained a full
     close → re-open → delete section (user-key 404s, 410s while
     closed, cookie minting/expiry, both links + edit form rendering
     the gone page, the plain 404 staying plain); `pollClient.do` now
     sends the urlencoded content type on empty-body POSTs like a
     browser. `go build`, `go vet`, `go test ./...` pass (no `-race` —
     this session's terminal ran unsandboxed on the Windows host,
     where no C compiler is available for cgo; the WSL sandbox that
     previously provided it was failing on a stale path
     `d:\devel\bimaru`). Note for future sessions: `write_file`
     mangled nested HTML in two template files during this session
     (injected stray `</p>`/`</div>`); always re-read template files
     after writing them.

     `background-clip: content-box` (border-box keeps the button at
     44px, so no row-height change). The existing forced-colors rule
     already outlines `button.mark`, so the flat state stays visible in
     high-contrast mode. No template/JS/Go changes.
