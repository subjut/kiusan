# Prompt log

Verbatim log of the prompts given to the agent in this repository, grouped
per session day. The prompts are the project's steering history: they
survive agent-session compaction and can be handed to a fresh agent
verbatim.

Conventions:

- Prompts are quoted exactly as given, typos and all.
- A short note follows each prompt: what it produced or decided.
- Entries marked *(wording lost)* belonged to a compacted conversation
  whose summary preserved only the substance.
- Transcript markers like "function call failed" in Zed's thread history
  are failed agent tool calls (e.g. truncated write batches), not user
  prompts, and are not logged here.
- Entries are appended automatically with every prompt — verbatim plus
  a one-line outcome note, written before the session summary (rule in
  `AGENTS.md` → Conventions).

## 2026-10-26 — poll answering feature: plan

1. "The general idea is to only collect as little data as possible to provide the scheduling service. This also means no user accounts. For each poll, there should be two links, one for admin, one for users answering the poll (the admin should also be able to answer the poll). The admin links should be created like the user links, which are already implemented.
The user poll page has a table with all date/meeting time options for selection. The user has to enter a name into a box and select all suitable options/dates/meeting times. The answer options are a green check mark, a yellow check mark in parentheses, and a red `X`. If the form indicated \"People can only sign up to one time slot\", make all other options greyed out when one option is selected. A selected option must be de-selectable, e.g. back into an unset state. Unset state means red `X` when the answer form is submitted. The user poll page should show all submitted answers, unless the \"Respondents can't see each others answers\" option is selected during poll creation. It should also display the description above the answer table.
For each new user, a cookie should be saved to the browser that identifies the user across browsing sessions. The cookie should be valid until the end of the poll, which defaults to three months or expire. When a known user returns to a poll which that user has already answered, there should be a button for the user to edit their answer and it should be possible for the user to delete their answer. If possible, the cookie should be deleted then.
The admin page should additionally display both links for copying and an edit poll button. That edit poll button should lead back to the 1-1-form page, but prefilled with the entries from the database. All changes should be written back to the same database entry for the poll without changing the user and admin links for the poll.
Initially, the Users database portion was meant to be for the purpose of identifying returning users for the editing answer feature. But maybe you have a better suggestion.
Make an implementation plan and present it to me. Ask me questions sooner rather than later when you are unsure about a feature. Don't change any code yet."
   → Codebase analysis (findings: `/meet/<key>` is still a plain-text
     dump; the two existing form checkboxes 400 the submission when
     checked — schema bool converter rejects `value="hide-users"`;
     Pudge serializes stored values via gob, so an embedded JSON-doc
     field round-trips on both backends). Asked 4 questions; decisions:
     one `/meet/<key>` route for both a user and an admin key (server
     picks the view from which key matched); single-slot mode omits the
     yellow option and is enforced server-side; the poll's end is an
     expiry date the admin picks in the 1-1 form (default 3 months out);
     expired polls are read-only for answers but the admin can still
     edit, including prolonging the end. Full implementation plan
     presented; no code changed.
2. "Assumption 3 addendum: The answer given on the admin page should also place a user cookie, so when the admin user opens the user page, his answer is editable for him. The admin should be able to edit all answers on the admin page, but only his answer on the user page.\nAnd assumption 5: explain CSRF token and the implications. I want this site secure.\nThe rest looks good."
   → Confirmed the admin's answer already reuses the per-poll cookie
     (no change). Plan delta: admin-key-authorized
     `/meet/<key>/answer/edit` (+ respondent-id delete) for managing
     any respondent from the admin page; fixed a v1 hole where the
     poll-edit flow accepted the user key, letting any respondent edit
     the poll (now admin-key-only). CSRF explained: identity endpoints
     are the real surface (public user link + cookie set on visit);
     mitigation = SameSite=Lax + stateless HMAC-SHA256 form token on
     cookie-identity endpoints (KIUSAN_SECRET for restart survival),
     X-Frame-Options: DENY / CSP frame-ancestors vs clickjacking,
     urlencoded-only bodies, template-escaping/textContent discipline;
     capability-keyed endpoints stay token-free.
3. "Continue where you left off"
   → (continuation of the same turn) plan delta delivered as above;
     still no code changed.
