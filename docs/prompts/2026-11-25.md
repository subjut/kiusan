1. "Read AGENTS.md. Bug: When the user clicks a link on a page, then changes the language on the new page, the language changes. But when the user clicks the browser back button and returns to the previous page, the language is the old one before the change, but the language dropdown displays the newly chosen language. The language should be the newly set language on the old page. Analyze why that happens and make a proposal to fix it."
   (supplement: "If the user reloads the page after using the browser back button, the language of the old page changes to the selected one.")
   → Analysis + proposal: the previous page is restored from the bfcache with its server-rendered (baked) locale while the `kiusan-locale` cookie — changed on the newer page — and the live dropdown already reflect the new language; scripts do not re-execute on bfcache restore, so nothing reconciles the frozen content. Proposal: a `pageshow` (persisted) handler in `locale.js` that detects a locale drift (resolve vs the page's parse-time `locale`) and re-applies it in place via the existing switch path (fetch `/i18n/<tag>` → `window.I18N` → `applyDict` → `applyLocale`), with a `syncSelect()` refactor for the dropdown and `location.reload()` as the fetch-failure fallback; jsdom tests planned for `jstest/locale_test.mjs`.

2. "Yes, implement the fix"
   → Implemented the proposal: `locale.js` gained the `syncSelect()` refactor (the parse-time select sync, now shared) and a `pageshow` handler that, on a bfcache restore (`persisted`) with a locale drift, re-syncs the dropdown and re-applies the locale in place through the existing switch path (fetch → `window.I18N` → `applyDict` → `applyLocale`), falling back to `location.reload()` while the dictionary is unreachable; four jsdom cases added to `jstest/locale_test.mjs`. jstest 47/47 pass; `AGENTS.md` updated (the locale-display gotcha, the static/js layout entry, the JS-tests coverage line).

3. "It seems to work for the form pages, but not for when going back from a form page to the home page."
   → The `e.persisted` gate was the flaw: pages come back two ways — a bfcache hit (parked DOM, `persisted=true`, body *and* `window.I18N` both stale → fetch the current dictionary) and a re-parse (`persisted=false`, scripts re-run: `/i18n/boot` carries no-cache, so `window.I18N` is *already* the current dictionary and the dropdown re-syncs to the cookie, while the body's `data-i18n` strings are the stale first-render ones → re-apply the current dictionary, no fetch). The home page is the session's first page — the bfcache entry most likely to be evicted — so it takes the re-parse path, which the persisted gate (and even a locale-drift gate: the locale variable agrees with the cookie on a re-parse) missed; recent form/meeting pages ride the bfcache and worked. The handler now converges the DOM onto the current locale on *every* `pageshow`: while `window.I18N` is the effective locale's dictionary (its `lang` compared onto the shipped tags via a new `tagOf()`, mirroring the server's `matchLang` — a base-tag fix the tests surfaced, `en` vs `en-US`) it re-applies in place (an idempotent no-op on a fresh render), while it is stale it fetches first; the dropdown re-syncs in both arms, `location.reload()` remains the fetch-failure fallback. The four restore tests were rewritten to seed `window.I18N` the way a real boot does (stale-dictionary bfcache fetch, current-dictionary re-parse re-apply, fresh-load no-fetch, failed-fetch no-op). jstest 48/48, `go build` / `go test ./...` green; `AGENTS.md` updated (gotcha, layout, JS-tests lines).
